## 已确认的官方定义

| 项目 | 官方定义 | 来源 |
| --- | --- | --- |
| ECS 源指标 | `SYS.ECS/network_vm_bandwidth_out` 为虚拟机整机每秒发送的流量，包含公网和内网总和；单位 `Byte/s`，KVM/QingTian 原始监控周期 5 分钟 | [1] |
| EIP 源指标 | `SYS.VPC/upstream_bandwidth` 为测量对象出云平台的网络速度；单位 `bit/s`，原始监控周期 1 分钟；支持 `publicip_id` 与 `bandwidth_id` 两种维度 | [2] |
| `period=1` | 查询监控资源的实时数据；批量 API 文档另明确其为原始值，此时 `filter` 不生效、默认 `average` | [3][4] |
| `period=300` | 聚合 5 分钟粒度数据，即每 5 分钟一个数据点 | [3][4] |
| `filter=average` | 聚合周期内原始指标数据的算术平均值 | [3][5] |
| 聚合时间戳 | 将一个周期内的数据点聚合到周期起始边界。例如 10:30～10:35 的原始数据聚合到 10:30 这个点 | [3][5][6] |
| 查询范围 | CES 按所选聚合粒度向前取整 `from`；API 建议 `from` 相对于当前时间向前偏移至少一个周期，以免聚合未完成而查询为空 | [3] |
| 采样周期影响 | 官方明确不同采样周期会使 ECS 网络流量与系统内工具结果不同，采样周期越大，短期内的数据失真越大 | [7] |

上述文档在本次核查中通过官方站点正常 HTTPS 读取，正文对应的 `.md` 地址由
官方 HTML 的 `rel="alternate" type="text/markdown"` 链接提供。

## 对本次问题的含义

现场 2026-10-30 14:10 的两个出站指标换算后分别为：
ECS 总量 `60,701.44 bit/s`、EIP 公网 `638,741.87 bit/s`，
估算差为 `-578,040.43 bit/s`。上一时间点 14:05 的 ECS 总量为
`746,128.08 bit/s`、EIP 公网为 `4,448.48 bit/s`。
这些是现场数据，不是官方文档的示例。

官方资料能说明，`period=300` 控制 CES 如何聚合源数据，
不会把每 5 分钟一个点的 ECS 原始采样变成每分钟采样。
因此，把两个源都请求为 `300/average`、再匹配返回时间戳，
只能确认其被归入同一个 CES 聚合桶，不能据此证明它们的原始速率值
覆盖完全相同的实际采样窗口。这个结论是依据上述定义的工程推理，
不是华为对这两个指标可直接相减的保证。

ECS 指标文档没有明确给出 `network_vm_bandwidth_out` 原始点的速率计算公式，
也没有说明它是瞬时值、前 5 分钟计数差分，或原始时间戳表示计算区间的起点还是终点。
因此，仅凭这些文档不能断言本次一定存在恰好 5 分钟的源时间错位。
前后两个时间点的波峰位置不同使“时窗错位”成为可以验证的假设，
但需要原始序列与更多连续窗口支持。

`Byte/s` 与 `bit/s` 的直接换算系数为 8。文档的进制列分别为 IEC/SI，
该列不构成把不带 K/M 前缀的原始字节速率再乘以 1024 的依据。
实际判别单位问题仍应以 API 返回的 `unit` 和原始值为证，
核对本地转换是否确为 `Byte/s × 8`、`bit/s × 1`。

## 可证伪的现场验证

1. 查询同一实例和其真实绑定 EIP 的 `period=1` 原始出站序列，再查询
   `period=300/average`。按实际原始时间戳重建 5 分钟桶，比较 CES 返回值。
   这能区分聚合实现问题与源采样差异。
2. 比较多个突发窗口中 ECS 与 EIP 的波峰位置。只有固定方向的偏移在多个
   窗口重复出现，才能支持固定源时间偏移；单一波峰不足以选择平移方向或秒数。
3. 分别记录两种 API 返回的原始单位、原始数值、转换后速率，检查是否存在
   8 倍、1000 倍或 1024 倍的系统性差异。
4. 核实 EIP 的 `publicip_id`、端口及公网地址与 ECS 的实际绑定关系，
   并排除误用了共享带宽的 `bandwidth_id`。绑定关系必须来自真实只读资源清单，
   不能通过名称或两条曲线形状猜测。

在没有完成这些检查之前，不应直接平移 5 分钟，也不应将负差补零。
后者会把未知的估算质量问题变成“已经确认内网流量为零”。

## 2026-10-30 14:26 现场验证结果

ECS 分别查询 `period=1/300`，EIP 分别查询 `period=1/60/300`，

### 已排查的候选原因

| 检查 | 现场结果 | 判断 |
| --- | --- | --- |
| 单位 | ECS 原始单位全部为 `B/s`，EIP 全部为 `bit/s`；代码分别乘 8 和 1 | 未发现单位换算错误 |
| 当前 EIP 关联 | 一个 EIP，公网地址和端口均匹配，完整 ECS 清单候选数为 1，公网地址无重复 | 当前清单不支持错误关联；不据此推断历史从未换绑 |
| ECS 聚合复算 | 144 个五分钟桶，每桶只有一个原始样本；本地均值与 API 聚合值最大差为 0 | ECS 的五分钟 `average` 在该窗口等于桶内单点值 |
| EIP 聚合复算 | 144 个桶，每桶均有五个分钟样本；复算均值与 API 聚合值最大差为 0.006 bit/s | 聚合符合文档，差异仅为数值舍入 |
| 固定五分钟时移 | 出站同桶相关系数 0.805964、14 个负差；EIP 后移五分钟为 0.622899、19 个负差；前移五分钟为 0.377355、23 个负差 | 本窗口不支持固定前后平移五分钟作为修正 |

时间偏移比较的定义为 `ECS[t]` 对 `EIP[t + shift]`；
零偏移匹配 144 点，正负五分钟各匹配 143 点。
这组对比用于检查简单的固定时移假设，不作为推导新算法或最优偏移的充分依据。

### 本次负差如何形成

ECS 的 144 个原始出站样本均位于聚合桶起点后 273 至 297 秒，
而 EIP 原始点位于每分钟边界。14:10 这个聚合桶中，两边的实际输入是：

| 来源 | 原始时间 | 换算后出站速率，bit/s |
| --- | --- | ---: |
| ECS 唯一原始样本 | 14:14:56 | 60,701.44 |
| EIP 原始样本 1 | 14:10:00 | 1,758,003.20 |
| EIP 原始样本 2 | 14:11:00 | 1,432,410.40 |
| EIP 原始样本 3 | 14:12:00 | 933.60 |
| EIP 原始样本 4 | 14:13:00 | 1,290.67 |
| EIP 原始样本 5 | 14:14:00 | 1,071.47 |

EIP 五个样本的均值是 `638,741.868 bit/s`，API 舍入为
`638,741.87 bit/s`。ECS 桶内只有一个值，均值仍为
`60,701.44 bit/s`，所以当前代码得到 `-578,040.43 bit/s`。
EIP 分钟序列的前两个点存在明显突发，而 ECS 的桶末样本没有反映出
同等幅度的高值。**相同的聚合标签，掩盖了单个 ECS 速率样本与
五个 EIP 分钟样本均值的统计基础差异。现有估算把它们当作可直接相减的
同一时段总量和子集，缺少这种可比性的保证。**

这解释了此次估算为何为负，而不表示实际内网流量小于零。
不能把 ECS 原始点进一步称为“瞬时值”：其底层速率计算公式和实际覆盖时段，
官方资料未明确说明，现场 API 也不提供这些信息。因此还不能确定
云侧采样、速率计算和上报时序各自贡献了多少偏差。
结论限于本实例和本次取证窗口，不把全部历史部分失败都归为相同原因。

### 对后续修复的约束

不能通过固定平移五分钟或将负差置零来宣称已修复。
若仍需要内网估算，应先选择已证明统计窗口和计算口径可比的数据源，
或向华为核实 ECS 原始速率的计算定义。当前源不满足这一保证时，
应将该实例标为估算不可用；通知策略可按数据质量与真正 API 请求失败分别设计。
截至这轮现场取证完成时，没有修改线上或本地运行算法。

## 后续采样试验与最终处理

追加验证比较了“EIP 取 ECS 源点所在分钟”的同分钟匹配方案。
不能仅比较负差总数并忽略发生在哪些桶：

| 比较项 | 五分钟平均原方案 | 同分钟匹配候选 |
| --- | ---: | ---: |
| 负差桶总数 | 14 | 15 |
| 原有负差中消失 | 不适用 | 12 |
| 原有负差仍存在 | 不适用 | 2 |
| 新增负差 | 不适用 | 13 |

因此候选的 15 个负差是 `2 + 13`，不能描述为改善或修复。
另外用 Agent 的原生分钟数据重建五分钟平均后，仍出现 15 个负差。
这两项试验都不支持“更换采样点或均值就能保证相减可用”的说法，
也不足以据此切换生产数据源。当前保留已有来源、`300/average`、
单位处理、源时间策略、账号/任务/渠道开关与告警阈值。

最终采用并部署“保留内网估算，负差单列不可用”：

- 只有有限负差是质量状态 `degraded`，不新增 `collection-error`；API、缺字段、非法单位、非有限值、缺失/陈旧/不对齐数据和映射错误仍为真实 `error`。
- 一个方向负差即不输出该资源任一方向，不补零。任务为 `ok` 或 `degraded` 时，其他仍新鲜且可用的资源继续展示；真实错误或任务陈旧时隐藏该估算任务全部当前值。
- 按任务、地域、资源持久化无效源时间，只有同一资源严格更新的有效入出站配对点才能确认恢复；旧点、其他资源成功或服务重启不能清除不可用状态。
- 不可用期间保留业务活动告警，中断阈值候选和业务恢复连续性，等待有效源点重新累计。只有负差的成功查询可按原次数参与采集健康告警恢复，与业务恢复分开。
- `/readyz` 接受 `degraded`，真实错误仍不通过。Prometheus 的 `cloud_monitor_network_estimate_available` 与独立 Grafana 可用性表显示已取得有效配对点或有负差记录的资源；指标不能替代任务状态和新鲜度检查。

这项改动管理估算质量，没有证明当前两种源在每个窗口都可精确相减。
正式服务首轮已核验 36 个资源可用、72 条双向估算；该首轮没有负差，负差路径由真实样本离线回放及回归测试验证。线上现用 Grafana 看板未应用新增表。完整行为约定见
[估算可用性](network-traffic.md#估算可用性)。
