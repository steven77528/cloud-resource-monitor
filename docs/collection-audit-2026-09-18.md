## 短信统计的具体处理

诊断得到的安全错误为：

```text
ValueError: SMS daily statistics missing dates: 2026-09-17, 2026-09-16, 2026-09-14, 2026-09-13, 2026-09-12, 2026-09-11, 2026-09-10
```

代码位于 `cloud_monitor/providers/aliyun.py` 的 `_sms_statistics`。成功的完全空列表返回 `no_data`；非空但日期不完整会报错。本次属于后者，不能套用 2026-09-09 文档中的“全空列表”历史结论。

1. 在同一阿里云账号的国内短信日报中，核实缺失日期确实未发送，还是日报没有返回。当前使用 `is_globe=1`，没有签名或模板过滤。
2. 若确认为零发送日，并确认此 API 用省略日期表示零发送，可据此调整采集逻辑：只有在请求成功、分页完整、统计窗口有效时补齐零发送日，同时保留对异常/未完成查询的错误判定。这是后续实现建议，本次没有补零或改代码。
3. 若无法确认缺失日期就是零，应保持增长率不可用；建议单独导出实际返回的日发送量和统计完整性，让不完整基线显示“统计不足”，并将真正的 API 失败单独告警。
4. 若业务发送很稀疏，可以改用日发送量绝对阈值或适合业务的统计窗口，避免为了生成百分比要求每天都存在记录。基线为零且昨日非零时，百分比增长本身也没有有限定义。
5. 单纯每小时重试未必解决，当前自然日内的 8 日窗口不变。不要通过真实发送短信来制造完整数据。

## 服务器复查

在服务器当前项目目录执行既有只读诊断：

```sh
docker compose run --rm --no-deps cloud-monitor --config /app/config/config.yaml diagnose --job aliyun-sms-statistics --job aliyun-slb-expiry --job aliyun-oss-packages --job huawei-slb-expiry
```

该命令使用实际只读云 API，会占用查询额度，但不实例化数据库或通知客户端。不要用 `once` 代替，它会持久化告警，之后可能由运行中的服务发送。

验收时分别看：短信是否有可信完整统计；两个到期任务是否确有适用的订阅；资源包是否有真实套餐记录。若没有适用业务数据，保持明确的“不适用/未接入”状态比填入零值更准确。
