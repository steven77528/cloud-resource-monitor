# 阿里云每月采集 API 调用量测算

核验日期：2026-09-08。依据当前 `config/config.yaml`、`cloud_monitor/providers/aliyun.py`，以及用户补充的“3 个 OSS Bucket、4 条 SLB，分布在不同账号”进行计算。本次仅核算和记录结论，未修改程序或采集频率。

## 结论

按每个 OSS Bucket 采集容量、请求量和公网流出流量，每条 SLB 采集入、出两个方向的带宽计算，31 天完整月份预计调用云监控查询 API **361,677 次**，30 天月份为 **350,010 次**。

官方规定，`DescribeMetricLast`、`DescribeMetricList`、`DescribeMetricData`、`DescribeMetricTop` 四种接口合计每月免费 **1,000,000 次**。本项目使用 `DescribeMetricList`。即使把上述资源都归入同一个主账号，本套采集计划也只占免费额度的 **36.1677%**；不同主账号分别计算时，本套计划对各账号的占用不会超过这个最坏情况。

因此，**当前采集频率本身满足该月度免费额度**。能否保证某个真实账号整月不超额度，还需要加上该账号已有的 Grafana、脚本或其他监控系统的调用量。由于尚未填写云密钥，本次没有查询各账号已经消耗的实际额度。

## 31 天明细

| 采集内容 | 资源数量 | 每个资源的指标数 | 频率 | 月调用量 |
| --- | ---: | ---: | --- | ---: |
| OSS 存储容量 | 3 | 1 | 每 24 小时 | 93 |
| OSS 请求量与公网流出流量 | 3 | 2 | 每 1 小时 | 4,464 |
| SLB 入、出方向带宽 | 4 | 2 | 每 1 分钟 | 357,120 |
| 合计 | | | | **361,677** |

计算过程：

```text
31 天 = 744 小时 = 44,640 分钟

OSS 容量：3 × 1 × 31                  =      93
OSS 请求/流量：3 × 2 × 744            =   4,464
SLB 入/出带宽：4 × 2 × 44,640         = 357,120
总计                                 = 361,677 次

最坏情况下集中在一个账号：
免费额度使用比例 = 361,677 ÷ 1,000,000 = 36.1677%
剩余额度         = 1,000,000 - 361,677 = 638,323 次
```

30 天月份同理：`3 × 30 + 3 × 2 × 720 + 4 × 2 × 43,200 = 350,010` 次。当前 2026 年 9 月有 30 天，350,010 是运行完整月份的计划量，不是从核验日起剩余日期的调用量。

## 不同账号如何计算

对每一个阿里云主账号，设该账号下配置的 OSS Bucket 数量为 B，SLB 监控对象数量为 L。在同样频率下：

```text
31 天云监控调用量 = 1,519 × B + 89,280 × L
实际月用量 = 本套采集调用量 + 同主账号其他系统调用量 + 额外分页或手工重跑等调用
```

这里的 L 是“一组入、出两个方向指标”的监控对象数。若同一 SLB 的多个监听器、端口都分别查询，就要按实际配置的监控对象或指标序列数计算，不能只计算 SLB 实例数。例如 4 个实例每个分别采集 3 个监听器，应按 12 组计算。在全部归入一个账号、3 个 Bucket 不变的例子中，12 组将达到 1,075,917 次，超过 100 万免费额度；实际分账号时仍需各自拆分核算。

RAM 用户、子用户、不同 AccessKey 不一定代表不同额度池。属于同一阿里云主账号的 RAM 用户，其 API 调用次数累计到同一主账号。若用户所说的“不同账号”是相互独立的主账号，则分别使用各自主账号的额度。

## 计数口径

- 本次按启用相关监控任务后、正常运行完整月份计算。模板中的账号和部分任务目前仍处于关闭状态，不能用关闭时的零调用量替代上线测算。
- 当前程序对每个资源、每个指标单独调用一次 `DescribeMetricList`。正常返回一页时，一次查询就是一次 API 调用；返回多个历史数据点不会按数据点数量重复计费。
- 额外的 `NextToken` 分页请求需追加计数。当前模板的查询时间窗和周期通常可在一页内返回，表中按一页估算。
- 启动首轮检查、重启、手工执行一次采集等操作可能增加调用量。P0 和 P1 共用同一次采集结果，不会因为配置两个告警等级就把采集请求翻倍。
- 本项目阿里云采集 SDK 设置了 `auto_retry=False`；通知队列的重试不等于云监控数据查询重试。
- 每分钟运行的短信回执成功率任务查询的是本地 MySQL 数据，不会每分钟向阿里云发起一次采集 API 请求。
- ECS/RDS 到期、域名、证书、账号余额、资源包和短信日统计分别调用其他服务的 API，不属于上述四种云监控查询接口的 100 万次免费池。不能把所有阿里云服务的查询总数混在一起比较这项额度。
- P0 告警短信发送另有短信服务费用及发送限制，不包含在本次云监控采集额度中。

## 月额度与每秒限流的区别

官方 `DescribeMetricList` 文档同时规定 **50 次/秒**的限流，同一阿里云账号及其 RAM 用户共享。月总量合格不代表任意瞬间都可以超过该速率。现有资源规模较小，但账号上的其他调用方、多个任务并发、快速分页仍需一起考虑。

其他服务也有自己的限流。例如证书列表接口 `ListUserCertificateOrder` 为单用户 10 次/秒，证书详情接口 `GetUserCertificateDetail` 为单用户 100 次/秒。ECS 的限流按账号、地域和 API 区分，实际账号配额应在官方配额页查询。部分其他接口的核查页面未明确给出月度总量，不能据此推断没有限制。

若 100 万次免费额度耗尽，**未开通基础云监控按量计费时，API 使用会受影响**；开通按量计费后，超额部分才会按相应规则计费。这里的 100 万不能简单理解为“到达后一定自动扣费、查询永远继续”。

当前 3 个 Bucket、4 组 SLB 指标无需为了月额度降低采集频率。建议保留 SLB 每分钟采集，以满足持续 5 分钟的告警判断；上线后分别查看每个主账号的 API 调用量，计入已有监控系统用量。单纯把 SLB 改成每 5 分钟查询一次，会改变持续告警判断的可靠性。
